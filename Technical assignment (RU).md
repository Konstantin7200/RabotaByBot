## 1 · Обзор

Мультипользовательский Telegram-бот, который отслеживает привязанные почтовые ящики Gmail
на предмет писем Rabota.by с ответами на отклики и отправляет уведомление в Telegram-чат
пользователя, привязавшего аккаунт.

**Цель продукта:** соискатели узнают об ответах (принят/отклонён) оперативно —
целевая задержка p95 ≤ 60 с в штатном режиме, — не проверяя почту.

## 2 · Область

### Входит в область

- Привязка / отвязка Gmail через OAuth для каждого пользователя Telegram — см. FR-2, FR-3, FR-9
- Команды бота `/start`, `/status`, `/unlink` — см. FR-1
- Push-обнаружение писем (Gmail watch → Cloud Pub/Sub → вебхук)
- Фильтрация: только отклики Rabota.by; извлечение вакансии / работодателя / исхода — см. FR-5, FR-6
- Доставка уведомлений в правильный Telegram-чат; дедупликация и хранение метаданных — см. FR-7, FR-8, FR-9
- Автоматическое продление watch; безопасное поведение при перезапуске — см. FR-10, FR-11
- Служебные страницы OAuth-редиректа (успех / ошибка) — не веб-приложение, а часть флоу; см. FR-3
- Оповещения о потере/восстановлении доступа и доставка пропущенных обновлений — см. FR-12 – FR-14

### Вне области

| Исключено | Причина |
|---|---|
| Полноценный веб-интерфейс | Управление — только через Telegram; страницы OAuth-редиректа служебные и входят в область |
| Дополнительные агрегаторы | Отложено — см. US-12 |
| Несколько ящиков на один чат | Отложено — см. US-13; в скоупе связь строго 1:1 (FR-15) |
| Полный парсинг / анализ писем | Извлекается только вакансия / работодатель / исход |
| Админ-панель, биллинг | Нет потребности при текущем личном распространении |
| Верификация Google | Первый релиз ≤ 100 пользователей (тестовый режим OAuth) |
| Хранение содержимого писем | Тело письма не сохраняется. В качестве метаданных хранятся: ID писем, `historyId`, дата последнего доставленного письма, заголовки From/Subject, разобранные поля уведомления, статус обработки, связка email↔chat, сроки watch/токена, журнал дедупликации — это необходимо для FR-1, FR-6 – FR-14, FR-15 |

## 3 · Функциональные требования

Роли идентификаторов: **email** — ключ дедупликации (FR-7); **chat** — цель доставки
(FR-8, FR-11); соответствие email↔chat задаёт FR-15 (строго 1:1 в скоупе).

| ID | Требование | Источник |
|----|------------|----------|
| FR-1 | Бот поддерживает команды `/start`, `/status`, `/unlink`. `/status` показывает привязанный email, срок действия входа и состояние отслеживания (watch); предупреждает, если что-то из этого истекло или бот не получает обновления. Срок входа вычисляется по времени его выдачи с учётом режима consent screen (в *testing* — 7 дней); в режиме production срок не задан (бессрочен при регулярном использовании; отзыва Google — пароль, политика, 6 месяцев неактивности — сохраняется) | US-2, US-3 |
| FR-2 | `/start` инициирует OAuth Google (offline access, scope `gmail.readonly`) со state, привязанным к chat ID. Для уже привязанного аккаунта повторный вход работает так же, как первоначальная привязка | US-1, US-8 |
| FR-3 | Колбэк OAuth сохраняет email + refresh token и устанавливает Gmail watch: (а) отвечает минимальной страницей в браузере (успех / ошибка), из которой пользователь возвращается в Telegram; (б) отправляет в Telegram подтверждение с привязанным email, а при отмене / сбое — понятное сообщение об ошибке. Правило базиса `historyId`: **повторная привязка после отвязки** (базис сброшен по FR-9) — базис берётся из ответа watch без ретроспективной дозаработки; **повторный вход при сохранённом базисе** (восстановление после сбоя) — сначала выполняется дозаработка FR-14. После успешной обработки каждого цикла (push или дозаработки) базис атомарно обновляется до последнего обработанного `historyId` | US-1, US-8 |
| FR-4 | Новые входящие письма обнаруживаются через push Gmail, а не поллинг | US-4; обеспечивает NFR «Задержка» |
| FR-5 | Уведомление отправляется только для писем, чей **домен отправителя** (в заголовке From по RFC 5322, не display name) принадлежит Rabota.by и которые соответствуют шаблону отклика | US-5 |
| FR-6 | Уведомление показывает вакансию/работодателя и исход; если разобрать письмо не удалось, показывается тема письма | US-4 |
| FR-7 | Каждое релевантное письмо порождает **одно** уведомление на ящик. Дедупликация по ключу `(email, gmail_message_id)`; ID сообщения Pub/Sub ключом не служит — одно push-уведомление может охватывать несколько писем, и на одно письмо может прийти несколько push. Журнал ведётся конечным автоматом из трёх состояний: `pending` (запись **до** отправки) → `sent` (после успешной отправки) \| `failed` (исчерпаны попытки, см. FR-11). Подтверждение обработки (ack) сообщения Pub/Sub даётся только после фиксации `sent` **или** надёжной записи `failed`: переигрывание `failed` — задача FR-14, а не повторных доставок Pub/Sub. Режим — at-least-once: падение между доставкой и фиксацией `sent` допускает единичный дубль; при восстановлении записи `pending` старше заданного порога X не переотправляются (трактуются как доставленные), поэтому массовых дублей не бывает. Журнал хранится не меньше максимального окна дозаработки FR-14; активные записи не очищаются | US-6 |
| FR-8 | Уведомления маршрутизируются в чат, связанный с email на момент доставки (финальной попытки — см. FR-11) | US-7, FR-15 |
| FR-9 | `/unlink` останавливает watch, отзывает refresh token у Google (`oauth2.revoke`), удаляет учётные данные и прекращает уведомления; по команде отправляется подтверждение отключения с перечнем отозванных доступов. Базис `historyId` сбрасывается: письма, пришедшие в период отвязки, при повторной привязке **не** доставляются. Журнал дедупликации сохраняется — ранее показанные уведомления не приходят заново | US-3, US-6 |
| FR-10 | Gmail watch продлевается автоматически не реже 1 раза в сутки, до истечения его 7-дневного срока (срок watch — свой, не зависит от режима consent screen) | US-8 |
| FR-11 | Отправка в Telegram выполняется **до** фиксации `sent` (FR-7); неудачные отправки повторяются с backoff и пределом попыток. Сообщения, исчерпавшие попытки, помечаются `failed` (FR-7) и переигрываются сверочным проходом FR-14. Целевой чат определяется на момент финальной попытки (перепривязка во время ретраев перенаправляет в новый чат; отказ уведомления старого чата о перепривязке допустим). Перезапуск сервера не приводит к потере уведомлений; дубликаты исключены механизмом FR-7, кроме задокументированного окна падения. Недостижимый чат (пользователь заблокировал бота) фиксируется со статусом и отражается в `/status` | US-6, US-2, US-11 |
| FR-12 | При потере доступа к ящику пользователь получает сообщение с причиной и инструкцией (обычно — повторить вход через `/start`). Механизм обнаружения: (а) истечение срока watch — по полю `expiration` из ответа `users.watch`, проверяется cron-задачей продления FR-10; (б) истечение refresh-токена — по факту ошибки `invalid_grant` при обновлении access token; (в) ошибки Gmail API при продлении/обработке — по коду ответа | US-9 |
| FR-13 | После восстановления доступа (повторный вход или устранение сбоя) пользователь получает подтверждение; после полного выключения сервера при запуске привязанным пользователям отправляется сообщение «снова на связи» | US-10 |
| FR-14 | Дозаработка выполняется для периодов недоступности, когда аккаунт был привязан: по сохранённому `historyId` через `history.list`; если `historyId` больше не действителен (404) — fallback на `messages.list` с фильтром по отправителю и дате от последнего доставленного письма, **но не раньше текущего базиса** (границы периода отвязки), а если доставленных ещё не было — от времени выдачи доступа. Дубликаты исключены механизмом FR-7; после успеха базис атомарно обновляется (FR-3). Триггеры: восстановление после сбоя, накопленные `failed`-отправки (FR-11) и ежесуточный сверочный проход от базиса (компенсирует молча потерянный push) | US-11 |
| FR-15 | Связь email↔chat строго 1:1: один ящик — один чат и наоборот. Повторная привязка ящика переводит уведомления в новый чат и отправляет прежнему чату уведомление о перепривязке (best-effort, см. FR-11); привязка нового ящика к чату, у которого уже есть ящик, отвязывает прежний — со всеми последствиями FR-9 (watch остановлен, токен отозван, базис сброшен, журнал дедупликации сохранён) | US-7 |

## 4 · Нефункциональные требования

| Область | Требование |
|---------|------------|
| **Задержка** | В штатном режиме (steady state, без холодного старта): письмо получено → сообщение в Telegram доставлено ≤ 60 с (p95). Потери при простое хостинга закрывает дозаработка FR-14; ретраи (FR-11) компенсируют кратковременные сбои доставки, а не задержку |
| **Квоты** | Запас в рамках бесплатного лимита Gmail API (~10 000 операций/пользователь/сутки) — ожидаемый объём ничтожен |
| **Безопасность** | Refresh-токены шифруются при хранении; вебхуки аутентифицированы: Telegram — secret token заголовком `X-Telegram-Bot-Api-Secret-Token`; Pub/Sub push — проверка OIDC-токена подписочной подписки (issuer Google, audience = URL эндпоинта); OAuth state защищён от CSRF, одноразовый, не переиспользуется |
| **Доступность** | Одноинстансное размещение допустимо; корректное завершение по SIGTERM; после полного выключения — сценарий FR-13 / FR-14 |
| **Ёмкость** | ≤ 100 пользователей (тестовый режим Google OAuth), распространение лично / в небольшой группе |
| **Наблюдаемость** | Структурированные логи для сценариев привязки, отправки уведомлений и продления; сбои видны через `/status` |

## 5 · Ограничения и выбор стека

| Вопрос | Решение |
|--------|---------|
| Среда выполнения | Node.js + TypeScript |
| HTTP-фреймворк | Express |

## 6 · Внешние интеграции

1. **Google Cloud** — проект с включённым Gmail API; OAuth client ID + зарегистрированный
   redirect URI; топик и push-подписка Pub/Sub; на топике выдана роль `roles/pubsub.publisher`
   сервисному аккаунту `gmail-api-push@system.gserviceaccount.com` (его Gmail использует для
   отправки push); экран согласия OAuth в режиме *testing* (≤ 100 пользователей).
   **Следствие тестового режима:** refresh-токены истекают через 7 дней — это влияет на UX:
   требуется периодический повторный вход, оповещение об истечении отправляет FR-12,
   а требование US-8 смягчено.
2. **Telegram** — бот создан через BotFather; вебхук зарегистрирован с secret token.
3. **Rabota.by** — обязательный вход до реализации FR-5 / FR-6: подтвердить адрес отправителя
   и шаблоны тем по реальному образцу письма с ответом на отклик. *(До подтверждения строка
   риска в §8 активна.)*

## 7 · Критерии приёмки / Готовность к релизу

- [ ] Все критерии приёмки из [`User stories (RU).md`](./User%20stories%20%28RU%29.md) (US-1 – US-11) проверены вручную end-to-end
- [ ] Сценарий истечения 7-дневнего refresh-токена проверен: пользователь получает сообщение FR-12, повторный вход через `/start` восстанавливает работу (FR-13), пропущенные обновления доставлены (FR-14)
- [ ] Watch продлевается автоматически (продление подтверждено в логах) не реже раза в сутки в течение срока жизни watch
- [ ] Смоделированные повторные доставки push от Pub/Sub и вебхука Telegram, а также перезапуски процесса: в штатных сценариях дубликатов нет (FR-7); потерь нет — FR-7 / FR-11 в штатном режиме, FR-14 после простоев; допустимое окно падения между доставкой и фиксацией проверено и не приводит к массовым дублям
- [ ] NFR проверены: задержка p95 ≤ 60 с в steady state; шифрование refresh-токенов; проверка secret token Telegram и OIDC push Pub/Sub; одноразовый OAuth state; корректный SIGTERM
- [ ] Lint и typecheck проходят
- [ ] Секреты не закоммичены; `.env.example` полон и документирован
- [ ] README с инструкциями по настройке, диаграммой архитектуры и заметками по деплою

## 8 · Риски и их устранение

| Риск | Влияние | Устранение |
|------|---------|------------|
| Refresh-токен истекает через 7 дней (тестовый режим Google) | Мониторинг останавливается; US-8 «без участия» выполняется только с повторным входом | Оповещение FR-12, безболезненная повторная привязка (US-8), верификация Google запланирована как будущий этап |
| Истечение 7-дневного watch молча останавливает push | Пользователи теряют уведомления | Ежесуточное cron-продление FR-10 + обнаружение по полю `expiration` и ошибкам продления (FR-12) + сверочный проход FR-14 + предупреждение через `/status` |
| Push не приходит, но сроки watch/токена в норме (редкая тихая деградация Google) | Уведомления приходят с задержкой до следующего сверочного прохода | Ежесуточный сверочный проход FR-14 компенсирует потерянный push; `/status` отражает состояние; принять как остаточный риск задержки |
| Крайний случай первого уведомления (нет предыдущего history ID) | Пропуск первого письма после привязки | Базовый снимок из ответа watch обязателен (FR-3); разница берётся только после него |
| `historyId` перестаёт действовать (404 после долгого простоя) | Дозаработка по FR-14 невозможна | Fallback на `messages.list` по отправителю и дате (FR-14) |
| Рабочий формат писем Rabota.by не подтверждён | Фильтр/парсер не работает | Подтвердить по реальному образцу до реализации FR-5 / FR-6 (§6.3) |
| Подделка отправителя (display name «Rabota.by» от чужого домена) | Бот рассылает фишинг как настоящие отклики | Фильтр по домену From по RFC 5322, не по display name (FR-5). Остаточный риск: подделка самого домена — принимается, вне скоупа (DKIM-проверка не входит) |
| Повторная доставка Pub/Sub | Дублирование уведомлений | Дедуп по ключу `(email, gmail_message_id)` и автомат `pending`/`sent` (FR-7); ID Pub/Sub не используется (одно письмо → много push, один push → много писем) |
| Падение между доставкой в Telegram и фиксацией `sent` | Единичный дубль уведомления | Допустимо и задокументировано (FR-7, US-6); окно узкое, поглощается сверкой `pending` |
| Полный простой сервера | Уведомления не отправляются, пока сервер недоступен | Ретраи Pub/Sub/Telegram + FR-13 «снова на связи» + FR-14 дозаработка |
| Чат недостижим (пользователь заблокировал бота) | Отправка падает бесконечно | Лимит попыток → `failed` → переигрывание (FR-11), статус виден в `/status` |
| Журнал дедупликации растёт | Рост таблицы со временем | Хранение ≥ окна дозаработки; очистка — только записей вне окна (FR-7) |
| Хостинг со спящим режимом (бесплатный Render) | Холодный старт нарушает NFR «Задержка» | Выбран хост без sleep (Railway / Fly.io); NFR сформулирован для steady state |
| Требование верификации Google для публичных пользователей | Блокирует широкое распространение | Сначала тестовый режим; верификацию запланировать позже |
