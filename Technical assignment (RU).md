# Техническое задание — Бот уведомлений Rabota.by

> Сопроводительный документ: [`User stories (RU).md`](./User%20stories%20(RU).md)
> Определяет, **что** должно делать система, её рамки и ограничения. Технический дизайн
> (архитектура, модель данных, API) описывается отдельно в технической спецификации.

---

## 1 · Обзор

Мультипользовательский Telegram-бот, который отслеживает привязанные почтовые ящики Gmail
на предмет писем Rabota.by с ответами на отклики и отправляет уведомление в Telegram-чат
пользователя, привязавшего аккаунт.

**Цель продукта:** соискатели узнают об ответах (принят/отклонён) в течение минуты,
не проверяя почту.

---

## 2 · Область

### Входит в область

- Привязка / отвязка Gmail через OAuth для каждого пользователя Telegram
- Push-обнаружение писем (Gmail watch → Cloud Pub/Sub → вебхук)
- Фильтрация: только отклики Rabota.by
- Доставка уведомлений в правильный Telegram-чат
- Автоматическое продление watch; безопасное поведение при перезапуске
- Минимальные страницы OAuth-редиректа (успех / ошибка) — см. FR-3
- Оповещения о потере/восстановлении доступа и доставка пропущенных обновлений — см. FR-12 – FR-14

### Вне области

| Исключено | Причина |
|---|---|
| Полноценный веб-интерфейс | Telegram-бот — единственный интерфейс; страницы OAuth-редиректа входят в область |
| Дополнительные агрегаторы | Отложено — см. US-12 |
| Полный парсинг / анализ писем | Извлекается только вакансия / работодатель / исход |
| Админ-панель, биллинг | Нет потребности при текущем личном распространении |
| Верификация Google | Первый релиз ≤ 100 пользователей (тестовый режим OAuth) |
| Хранение содержимого писем | Содержимое не сохраняется; метаданные (ID писем, статус обработки) хранятся — это необходимо для FR-7 и FR-14 |

## 3 · Функциональные требования

| ID | Требование | Источник |
|----|------------|----------|
| FR-1 | Бот поддерживает команды `/start`, `/status`, `/unlink` | US-1 – US-3 |
| FR-2 | `/start` инициирует OAuth Google (offline access, scope `gmail.modify`) со state, привязанным к chat ID | US-1 |
| FR-3 | Колбэк OAuth сохраняет email + refresh token, устанавливает Gmail watch и отвечает минимальной страницей (успех / ошибка), из которой пользователь возвращается в Telegram | US-1 |
| FR-4 | Новые входящие письма обнаруживаются через push Gmail, а не поллинг | US-4 |
| FR-5 | Уведомление отправляется только для писем, чей **домен отправителя** (в RFC 822-заголовке From, не display name) принадлежит Rabota.by и которые соответствуют шаблону отклика | US-5 |
| FR-6 | Уведомление содержит вакансию/работодателя и исход (best effort; запасной вариант — тема/сниппет) | US-4 |
| FR-7 | Каждое релевантное письмо порождает **ровно одно** уведомление на пользователя: дедупликация по ключу `(user_id, gmail_message_id)`. ID сообщения Pub/Sub ключом не служит — одно push-уведомление может охватывать несколько писем, и на одно письмо может прийти несколько push | US-6 |
| FR-8 | Уведомления маршрутизируются только в привязанный чат | US-7 |
| FR-9 | `/unlink` останавливает watch, удаляет сохранённые учётные данные и прекращает уведомления | US-3 |
| FR-10 | Gmail watch продлевается автоматически до истечения его 7-дневного срока | US-8 |
| FR-11 | Перезапуск сервера не приводит к потере уведомлений; дубликаты исключены дедупликацией FR-7 | US-6, US-11 |
| FR-12 | При потере доступа к ящику (истёкший refresh token, отвалившийся watch, ошибка Gmail API) пользователь получает сообщение с причиной и инструкцией (обычно — повторить вход через `/start`) | US-9 |
| FR-13 | После восстановления доступа (повторный вход или устранение сбоя) пользователь получает подтверждение; после полного выключения сервера при запуске привязанным пользователям отправляется сообщение «снова на связи» | US-10 |
| FR-14 | После недоступности доставляются все пропущенные отклики Rabota.by (по сохранённому `historyId`), без дубликатов уже доставленных | US-11 |
| FR-15 | Один почтовый ящик привязан максимум к одному чату: повторная привязка того же email переводит уведомления в новый чат | US-7 |

## 4 · Нефункциональные требования

| Область | Требование |
|---------|------------|
| **Задержка** | Письмо получено → сообщение в Telegram доставлено ≤ 60 с (p95) в steady state, без учёта холодного старта хостинга; простой хостинга компенсируется ретраями Pub/Sub/Telegram и дозаработкой FR-14 |
| **Квоты** | Запас в рамках бесплатного лимита Gmail API (~10 000 операций/пользователь/сутки) — ожидаемый объём ничтожен |
| **Безопасность** | Refresh-токены шифруются при хранении; вебхуки аутентифицированы (secret token Telegram + аутентификация push Pub/Sub); OAuth state защищён от CSRF и не переиспользуется |
| **Доступность** | Одноинстансное размещение допустимо; корректное завершение по SIGTERM; после полного выключения — сценарий FR-13 / FR-14 |
| **Ёмкость** | ≤ 100 пользователей (тестовый режим Google OAuth), распространение лично / в небольшой группе |
| **Наблюдаемость** | Структурированные логи для сценариев привязки, отправки уведомлений и продления; сбои видны через `/status` |

## 5 · Ограничения и выбор стека

| Вопрос | Решение |
|--------|---------|
| Среда выполнения | Node.js + TypeScript |
| HTTP-фреймворк | Express |
| Фреймворк бота | grammY — **режим вебхуков** |
| База данных | PostgreSQL |
| ORM | Drizzle (+ миграции drizzle-kit) |
| Gmail-клиент | `googleapis` |
| Транспорт push | Push-подписка GCP Pub/Sub → HTTPS-эндпоинт |
| Хостинг | Railway / Fly.io — нужен публичный HTTPS и хост **без спящего режима** (бесплатный тариф Render засыпает и не подходит под NFR «Задержка») |

## 6 · Внешние интеграции

1. **Google Cloud** — проект с включённым Gmail API; OAuth client ID + зарегистрированный
   redirect URI; топик и push-подписка Pub/Sub; право publish для сервис-аккаунта Pub/Sub;
   экран согласия OAuth в режиме *testing* (≤ 100 пользователей).
   **Следствие тестового режима:** refresh-токены истекают через 7 дней — часть UX
   (повторный вход), оповещение через FR-12, смягчённое требование US-8.
2. **Telegram** — бот создан через BotFather; вебхук зарегистрирован с secret token.
3. **Rabota.by** — адрес отправителя и шаблоны тем писем подтверждены по реальному
   образцу письма с ответом на отклик. *(Обязательный вход до реализации FR-5 / FR-6.)*

## 7 · Критерии приёмки / Готовность к релизу

- [ ] Все критерии приёмки из [`User stories (RU).md`](./User%20stories%20(RU).md) (US-1 – US-11) проверены вручную end-to-end
- [ ] Сценарий истечения 7-дневнего refresh-токена проверен: пользователь получает сообщение FR-12, повторный вход через `/start` восстанавливает работу (FR-13), пропущенные обновления доставлены (FR-14)
- [ ] Watch продлевается автоматически (продление подтверждено в логах) в течение срока жизни токена

- [ ] Lint и typecheck проходят
- [ ] Секреты не закоммичены; `.env.example` полон и документирован
- [ ] README с инструкциями по настройке, диаграммой архитектуры и заметками по деплою

## 8 · Риски и их устранение

| Риск | Влияние | Устранение |
|------|---------|------------|
| Refresh-токен истекает через 7 дней (тестовый режим Google) | Мониторинг останавливается, US-8 «без участия» выполняется только с повторным входом | Оповещение FR-12, безболезненный ре-линк (US-8), верификация Google запланирована как будущий этап |
| Истечение 7-дневного watch молча останавливает push | Пользователи теряют уведомления | Ежедневное cron-продление FR-10 + предупреждение через `/status` и FR-12 |
| Крайний случай первого уведомления (нет предыдущего history ID) | Пропуск первого письма после привязки | Базовый снимок при установке watch; разница берётся только после него |
| Неизвестен точный формат писем Rabota.by | Фильтр/парсер не работает | Получить реальный образец письма до написания FR-5 / FR-6 |
| Подделка отправителя (display name «Rabota.by» от чужого домена) | Бот рассылает фишинг как настоящие отклики | Фильтр по домену RFC 822 From, не по display name (FR-5) |
| Повторная доставка Pub/Sub | Дублирование уведомлений | Дедуп по ключу `(user_id, gmail_message_id)`; ID Pub/Sub не используется (одно письмо → много push, один push → много писем) |
| Полный простой сервера | Уведомления не отправляются, пока сервер недоступен | Ретраи Pub/Sub/Telegram + FR-13 «снова на связи» + FR-14 дозаработка по `historyId` |
| Хостинг со спящим режимом (бесплатный Render) | Холодный старт нарушает NFR «Задержка» | Выбран хост без sleep (Railway / Fly.io); NFR сформулирован для steady state |
| Требование верификации Google для публичных пользователей | Блокирует широкое распространение | Сначала тестовый режим; верификацию запланировать позже |
